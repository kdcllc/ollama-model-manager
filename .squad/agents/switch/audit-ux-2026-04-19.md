# UX Accessibility & Interaction Audit
**Date:** 2026-04-19  
**Reviewed:** `public/index.html`, `public/styles.css`, `public/app.ts`  
**Status:** **APPROVAL BLOCKED** — Multiple critical accessibility gaps and interaction risks identified.

---

## Executive Summary

The current implementation has **good visual polish** but **critical accessibility gaps** that block approval:
- **No keyboard focus indicators** on any interactive elements
- **Incomplete ARIA labeling** (only 2 of ~40+ form/interactive elements have labels)
- **No tab order management** (natural DOM order is reasonable but undocumented)
- **Focus not managed** when details panel opens (users TAB from nowhere to know where)
- **No keyboard shortcuts** for critical workflows (only global "/" search trigger)
- **Semantic HTML gaps** (buttons without labels, form grouping unclear)

**Blocker:** Keyboard-first users cannot use this UI effectively. Screen reader users cannot identify most form controls.

---

## Detailed Findings

### 1. **Focus Indicators: CRITICAL BLOCKER**

**Current State:**
- Zero CSS rules for `:focus` or `:focus-visible`
- Buttons have only `:hover` (visual transform)
- Inputs have no visible focus state

**Impact:**
- Keyboard user cannot see where focus is
- Tab navigation is invisible and confusing
- Screen reader users have no "sighted" peer experience

**Evidence:**
```css
.btn:hover {
  transform: translateY(-1px);
  transition: 120ms ease;
}
/* No :focus or :focus-visible rule exists */
```

**Test:**
- Tab through page in browser: No visual indication of focused element
- Expected: Ring, background change, or color shift on focused button/input

---

### 2. **ARIA Labels & Semantic Issues: CRITICAL BLOCKER**

**Current Labels (2/40+ controls):**
```html
<select id="modelSortSelect" aria-label="Sort models">
<div class="view-toggle" role="group" aria-label="Model display mode">
```

**Missing Labels:**
| Element | Why Critical | Current State |
|---------|-----------|---------------|
| Refresh Models button | No text reason | `id="refreshBtn"` — no label |
| Update Ollama Runtime button | No text reason | `id="updateOllamaBtn"` — no label |
| Pull/Update model button | Dynamic; uses template | `.pull-btn` on card — no aria-label |
| Delete model button | Destructive; needs confirmation context | `.delete-btn` on card — no aria-label |
| Model search input | Not semantic `<search>` or linked | `id="modelSearchInput" type="search"` with placeholder only |
| Details panel View button | No label | Card template `.view-btn` — no label |
| Save buttons | Multiple contexts | `id="saveOptimizationBtn"`, `id="saveMetadataBtn"` — generic button text |
| GPU toggles | No indication of state | `toggleGpuLiveBtn`, `refreshGpuBtn` — no aria-label or aria-pressed |
| Clear search button | Hidden purpose | `id="clearModelSearchBtn"` — button text only |

**Impact:**
- Screen reader users hear "button" instead of "Delete model llama3.2"
- Assistive tech cannot convey button purpose or model context

**Code Evidence:**
```html
<!-- Pull form has NO label association -->
<form id="pullForm" class="inline-form">
  <input id="pullName" type="text" placeholder="Example: llama3.2:3b-instruct-q4_K_M" required />
  <button type="submit" class="btn btn-primary">Pull or Update</button>
</form>

<!-- Create form fields have NO <label> elements -->
<form id="createForm" class="stack-form">
  <input id="createName" type="text" placeholder="..." required />
  <textarea id="createModelfile" rows="6" placeholder="..." required></textarea>
  <button type="submit">Create Model</button>
</form>
```

### 3. **Focus Management: CRITICAL BLOCKER**

**Current Behavior:**
1. User clicks "Details" on a model card
2. Code scrolls to `detailsPanel` but **does not move focus**
3. User continues tabbing from wherever they were
4. User is confused about what opened

**Code:**
```typescript
async function showDetails(name) {
  state.selectedModel = name;
  updateModelsDisplay();
  
  el.detailsContent.innerHTML = `<p class="hint">Loading details...</p>`;
  
  // Scrolls viewport but DOES NOT manage focus
  document.getElementById("detailsPanel").scrollIntoView({ 
    behavior: "smooth", 
    block: "start" 
  });
  
  // No: el.detailsPanel.focus() or el.detailsPanel.querySelector('input').focus()
}
```

**Impact:**
- Keyboard users cannot navigate to newly opened content
- Screen reader announces viewport scroll but not that new content is ready
- Experience is jarring for users not relying on mouse/visual continuity

---

### 4. **Tab Order: NOT PROBLEMATIC, BUT UNDOCUMENTED**

**Current State:**
- No `tabindex` attributes anywhere (good—uses natural DOM order)
- Natural order is mostly reasonable (top-to-bottom, left-to-right)
- BUT: Filter chips and model cards are rendered dynamically with no explicit order

**Concern:**
- Model cards rendered from template with click handlers but **no keyboard interaction**
- Chips can be clicked but **not focused/selected via keyboard**
- If layout changes, natural order may become wrong without tests

**Evidence:**
```typescript
// Card buttons are attached dynamically
fragment.querySelector(".view-btn").addEventListener("click", () => showDetails(model.name));
fragment.querySelector(".pull-btn").addEventListener("click", () => pullModel(model.name));
fragment.querySelector(".delete-btn").addEventListener("click", () => deleteModel(model.name));

// But they can ONLY be triggered by click, not keyboard
// No: addEventListener("keydown", e => e.key === "Enter" && ...)
```

---

### 5. **Keyboard Shortcuts: MINIMAL COVERAGE**

**Implemented:**
- `/ (slash)` → Focus search input (good shortcut)
- `Escape` in search → Clear search (good UX)

**Missing:**
- No `Enter` handling on model cards (can't pull/delete via keyboard)
- No navigation shortcuts (e.g., arrow keys to move between cards)
- No shortcut for "View Details"
- No shortcut for "Delete Model" with confirmation

**Evidence:**
```typescript
document.addEventListener("keydown", (event) => {
  if (event.key !== "/") return;
  // Only "/" is handled globally
  el.modelSearchInput.focus();
  el.modelSearchInput.select();
});
```

### 6. **Tabbed Layout Evaluation**

**Question:** Would a tabbed layout improve UX?

**Answer:** **Yes, conditionally. Tabbed layout would improve:**

1. **Cognitive Load:** Currently, all sections (System Profile, GPU Monitor, Install, Create, Models, Details, Activity) are stacked vertically. Users must scroll past unneeded sections to find task.

2. **Proposed Tab Structure:**
   - **"Models"** → Search, sort, filter, view installed models (primary)
   - **"System"** → Health, recommendations, GPU status, env vars
   - **"Actions"** → Pull/update, create custom model
   - **"Activity"** → Lifecycle history and logs
   - **"Config"** → Optimization preferences

3. **Accessibility Benefits:**
   - Clearer visual hierarchy
   - Reduced cognitive load (fewer elements visible at once)
   - Standard WAI-ARIA `tablist` pattern reduces learning curve
   - Better mobile UX (tabs collapse panels instead of full-height scroll)

4. **Implementation Risks:**
   - **Must implement tab keyboard interaction:**
     - `Left/Right arrow` to navigate tabs
     - `Tab` to enter tab content (first focusable element)
     - `Escape` to return to tab list (optional)
   - **Currently missing:** No tab keyboard handling in codebase

5. **Recommendation:** **Tabbed layout is a GOOD IDEA** but requires adding keyboard shortcut handlers. Without those, tabs are **equally inaccessible** as current layout.

## Concrete Interaction Risks

### Scenario 1: Keyboard-Only User Pulls a Model
1. User lands on page, presses `/` → Search input focused ✅
2. User types `llama2` → Models filtered (if search works) ✅
3. User presses `Tab` → Focus moves to... **unknown** ❌
4. User expects to reach "Update" button on first model card but **cannot see focus ring** ❌
5. User presses `Enter` thinking it will pull, but **button receives click**, not keyboard event handler ⚠️

**Failure Mode:** If card button does not have `Enter`/`Space` handler, nothing happens.

### Scenario 2: Screen Reader User Deletes a Model
1. User navigates to Details panel
2. Screen reader announces: *"Details empty"* (panel title, no context)
3. User clicks Details button, page scrolls but **screen reader announces nothing** ❌
4. User still does not know a panel opened
5. User re-clicks Details, now hears new content but **"Save" button has no aria-label** — announces as "button" ❌

**Failure Mode:** User cannot tell what action buttons do.

### Scenario 3: Mobile User with Physical Accessibility Needs
1. User relies on hardware keyboard connected to phone
2. Current layout: all sections stacked vertically
3. User must scroll past "System Profile", "GPU", "Install", "Create" to reach "Models"
4. With tabbed layout: one `Tab` keystroke switches between major sections
5. **Benefit:** ~5 fewer scroll events needed

**Win:** Tabs improve this but only if keyboard shortcuts are implemented.

## Recommendations Before Approval

### MUST-FIX (Blockers)

1. **Add CSS focus indicators** (5 min)
   ```css
   .btn:focus-visible,
   input:focus-visible,
   select:focus-visible,
   textarea:focus-visible {
     outline: 2px solid var(--accent);
     outline-offset: 2px;
   }
   ```

2. **Add ARIA labels to all buttons** (30 min)
   ```html
   <button id="refreshBtn" class="btn" aria-label="Refresh model list">Refresh Models</button>
   <button class="btn btn-small delete-btn" aria-label="Delete {modelName}">Delete</button>
   ```

3. **Manage focus when details panel opens** (15 min)
   ```typescript
   async function showDetails(name) {
     // ... existing code ...
     document.getElementById("detailsPanel").scrollIntoView({ behavior: "smooth", block: "start" });
     
     // NEW: Move focus to first input in details panel
     const firstInput = el.detailsContent.querySelector('input, textarea, button');
     if (firstInput) firstInput.focus();
   }
   ```

4. **Add semantic labels to forms** (20 min)
   ```html
   <form id="pullForm" class="inline-form">
     <label for="pullName">Model name:</label>
     <input id="pullName" type="text" required />
     <button type="submit" class="btn btn-primary">Pull or Update</button>
   </form>
   ```

5. **Add keyboard support to model cards** (25 min)
   - Delete button: `keydown` handler for `Enter`/`Space`
   - Pull button: `keydown` handler for `Enter`/`Space`
   - View button: `keydown` handler for `Enter`/`Space`

### SHOULD-FIX (Recommended)

6. **Implement tabbed layout** (if addressing cognitive load)
   - Requires WAI-ARIA tablist pattern
   - Add `aria-selected`, `role="tab"`, `tabindex` management
   - Implement Left/Right arrow key navigation

7. **Document tab order** in `.squad/decisions.md`
   - Specify which sections are in natural order
   - Flag any dynamic elements that may break order

## Conclusion

**Current UX is visually polished but accessibility-hostile.** Focus indicators are the single biggest win. After that, ARIA labels and focus management will unlock keyboard + screen reader support for ~95% of users.

**Estimated effort to fix:** 90 minutes.  
**Estimated effort to add tabbed layout + keyboard nav:** Additional 4-6 hours (not required for approval, but recommended for usability).

**Recommendation:** Fix blockers (1-5 above), then consider tabbed layout as Phase 2 improvement.
